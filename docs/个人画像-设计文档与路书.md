## 一、背景与目标

### 1.1 起因

在 `[[常用事项记录]]` 中有一个"人物画像刻画专题"，列了 7 个信息渠道。本设计文档将这个专题落地为可执行的系统。

### 1.2 核心目标

让"自己"这个系统可观测。

具体来说：用分散在各平台的个人数据，生成一份动态更新的个人画像文档，替代"靠感觉"的自我认知，为决策提供客观依据。

### 1.3 阶段定义

| 阶段 | 消费方 | 产出形态 | 时间 |
|------|--------|---------|------|
| 阶段一（当前） | 本人 | Obsidian 本地 md 文档 | 2026-07 起 |
| 阶段二（后续） | AI 助手 | 结构化字段 + 查询接口 | 阶段一跑通后 |

### 1.4 设计原则

- 零框架依赖：纯标准库 Python，不引入 HPI 等框架
- 一个源一个脚本：借鉴 qs_ledger 模式，每个数据源独立脚本
- 最小开销：能直接读文件就不建服务，能写死路径就不搞配置系统
- 与现有体系闭环：画像产出直接反哺信息层 SOP

## 二、画像维度设计

画像回答 5 个核心问题，每个问题对应一个可观测维度。

### 2.1 方向真实度

问题：你声称的方向 vs 实际在做的方向，gap 多大？

| 项 | 内容 |
|----|------|
| 数据源 | trae 聊天记录（intent 主题聚类）、marvis 聊天记录 |
| 产出 | 方向漂移检测报告（按周/月） |
| 反哺 | 信息层 SOP 第零层 · 方向校准 |
| 判断逻辑 | 声称方向（Agent/Memory）vs 实际讨论主题 TOP10 的重合度 |

### 2.2 知识兴趣光谱

问题：你真正在消费什么内容？

| 项 | 内容 |
|----|------|
| 数据源 | bilibili 观看历史（分类/标签）、trae 讨论主题 |
| 产出 | 兴趣分布 + 深度 vs 碎片比例 |
| 反哺 | 信息层 SOP 第一层 · 信源审计 |
| 判断逻辑 | 内容分类分布、时长分布、知识类 vs 娱乐类比例 |

### 2.3 作息精力模式

问题：你的高效时段是什么时候？

| 项 | 内容 |
|----|------|
| 数据源 | trae/marvis 活跃时间戳、weiTracker 拍照时间 |
| 产出 | 24 小时活跃度分布（文字版热力图） |
| 反哺 | 信息层 SOP 第二层 · L3 时间预算安排 |
| 判断逻辑 | 按小时统计活跃频次，识别峰值时段 |

### 2.4 决策行动模式

问题：你遇到问题时怎么处理？

| 项 | 内容 |
|----|------|
| 数据源 | trae 聊天记录（intent -> actions -> outcome 链） |
| 产出 | 决策模式画像（先调研 vs 先动手、想法到行动的间隔） |
| 反哺 | 工作流优化 |
| 判断逻辑 | actions 中"搜索/调研"vs"动手/实现"的比例、intent 提及到 actions 执行的时间差 |

### 2.5 情绪审美倾向

问题：你的情绪状态和审美偏好是什么？

| 项 | 内容 |
|----|------|
| 数据源 | 网易云听歌历史、bilibili 内容类型 |
| 产出 | 情绪曲线（按周/月）、审美偏好标签 |
| 反哺 | 自我状态监测 |
| 判断逻辑 | 音乐风格分布、播放时段、重复播放模式 |

## 四、技术方案

### 4.1 核心决策：直接脚本模式

不引入 HPI 框架。理由：

| HPI 能力 | 本场景是否需要 |
|---------|--------------|
| 配置层（路径管理） | 不需要，数据在固定目录 |
| cachew 缓存机制 | 不需要，JSONL/SQLite 读取就几秒 |
| namespace package 扩展 | 不需要，单人使用不发布 |
| 跨平台互操作 | 不需要，数据源固定 7 个 |
| 官方模块复用 | 不需要，全是英文平台 |

### 4.2 技术选型

- 语言：Python 3（标准库为主）
- 依赖：仅 sqlite3、json、glob、collections、datetime 等标准库
- 数据结构：用 `@dataclass` 统一各源的数据结构，方便后续多源融合
- 产出：Markdown 文档（直接写入 Obsidian）

### 4.3 脚本设计模式

每个数据源脚本遵循统一结构：

```python
# 1. 数据结构定义
@dataclass
class SessionRecord:
    time: datetime
    intent: str
    actions: list
    outcome: str
    learned: list
    source: str  # "trae" / "marvis" / ...

# 2. 数据读取函数
def load_records() -> list[SessionRecord]:
    """从数据源读取，返回统一结构"""
    ...

# 3. 分析函数
def analyze_direction(records) -> dict:
    """方向漂移检测"""
    ...

def analyze_active_hours(records) -> dict:
    """活跃时段分析"""
    ...

# 4. 输出函数
def generate_markdown(results) -> str:
    """生成 Markdown 报告"""
    ...

# 5. 主流程
if __name__ == "__main__":
    records = load_records()
    results = {
        "direction": analyze_direction(records),
        "active_hours": analyze_active_hours(records),
    }
    md = generate_markdown(results)
    # 写入 Obsidian
```

### 5.2 共享模块设计（common.py）

```python
# common.py - 各脚本共享的数据结构和工具
from dataclasses import dataclass, field
from datetime import datetime
from typing import Optional

@dataclass
class ChatRecord:
    """统一聊天记录结构"""
    time: datetime
    content: str           # 消息内容/意图
    actions: list = field(default_factory=list)
    outcome: str = ""
    learned: list = field(default_factory=list)
    source: str = ""       # trae / marvis / qq

@dataclass
class ContentRecord:
    """统一内容消费记录结构"""
    time: datetime
    title: str
    category: str = ""
    duration: int = 0      # 秒
    source: str = ""       # bilibili / netease / xhs

def write_markdown(path: str, content: str):
    """写入 Obsidian md 文件"""
    with open(path, "w", encoding="utf-8") as f:
        f.write(content)
```

## 七、与现有体系的关联

### 7.1 信息层 SOP 的闭环

```
信息层 SOP                          个人画像
---------                          --------
第零层 · 方向校准  <--- 反哺 ---  方向真实度（画像维度1）
第一层 · 信源审计  <--- 反哺 ---  知识兴趣光谱（画像维度2）
第二层 · L3时间预算 <--- 反哺 --- 作息精力模式（画像维度3）
```

画像把 SOP 里"靠感觉"的校准变成"有数据"的校准。

### 7.2 方向锚点

当前方向档案：
- 主方向：Agent
- 次方向：Memory

画像的方向真实度分析会直接检验：你在 trae/marvis 里实际讨论的主题，跟这两个方向的重合度。

### 7.3 操作台关联

`[[00-操作台]]` 中的月度校准记录表，后续可引用画像数据作为校准依据。

## 八、风险与应对

| 风险 | 概率 | 应对 |
|------|------|------|
| bili-cli / 网易云 API 不可用 | 中 | Phase 2 开始前先验证数据获取链路，不通就跳过该源 |
| marvis SQLite 读取时被锁 | 中 | 读取前复制 data.db 到临时目录再读 |
| 分析脚本写完不维护 | 高 | 每个脚本独立，挂了不影响其他源；Phase 4 加定期刷新降低手动成本 |
| 数据量不够分析不出趋势 | 中 | Phase 1 先用已有数据跑，数据不够就标注"样本不足，待积累" |
| 画像文档变成"写了不看" | 高 | 与操作台月度校准绑定，强制每月看一次 |
