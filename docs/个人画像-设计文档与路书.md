## 一、背景与目标

### 1.1 起因

在 `[[常用事项记录]]` 中有一个"人物画像刻画专题"，列了 7 个信息渠道。本设计文档将这个专题落地为可执行的系统。

### 1.2 核心目标

让"自己"这个系统可观测。

具体来说：用分散在各平台的个人数据，生成一份动态更新的个人画像文档，替代"靠感觉"的自我认知，为决策提供客观依据。

### 1.3 阶段定义

| 阶段 | 消费方 | 产出形态 | 时间 |
|------|--------|---------|------|
| 阶段一（当前） | 本人 | Obsidian 本地 md 文档 | 2026-07 起 |
| 阶段二（后续） | AI 助手 | 结构化字段 + 查询接口 | 阶段一跑通后 |

### 1.4 设计原则

- 零框架依赖：纯标准库 Python
- 一个源一个脚本：每个数据源独立的读取器
- 数据优先于分析：先把不同渠道的原始数据归一化落库，再谈上层分析
- LLM 增强语义：关键词统计只解决"有什么"，LLM 解决"意味着什么"
- 可降级：LLM 不可用时回退到规则分析
- 保持现有目录结构：不改 io/analysis/cli 的命名，只在其内部扩展

## 二、整体架构

系统分为两阶段：数据归一化存 SQLite，画像生成直接输出 md+json 文件。

```
[Channel原始数据]
       ↓ io/ 读取器
[raw_data 表] ← 统一结构，持久化
       ↓ llm/ 意图提取（短文本跳过LLM，直接入库）
[llm_intents 表] ← 结构化意图
       ↓ analysis/ 分 channel 分析（LLM 驱动）
       ↓ analysis/aggregator 融合
[md + json 文件] ← 按日期输出到 Obsidian
       ↓ refresh/ diff（对比上次 json）
[变化报告 md] ← 标记变化项
```

数据库只存前两层（raw_data + llm_intents），画像和变化报告全部以文件形式输出。

### 2.1 为什么这样分

| 层级 | 存储方式 | 原因 |
|------|---------|------|
| raw_data + llm_intents | SQLite | 需要增量入库、去重、跨运行复用，必须持久化 |
| 分 channel 画像 + 综合画像 | md + json 文件 | 画像是给人看的，按日期存文件更直观；json 供 diff 用 |
| 变化报告 | md 文件 | 直接在 Obsidian 里看，不需要查数据库 |

| 对比 | 原方案 | 新方案 |
|------|--------|--------|
| Reader | 直接返回内存对象 | 增加 ingest() 写入 SQLite |
| 分析 | 直接读原始文本 | 读 LLM 提取的意图 |
| 综合画像 | 多源拼接 | LLM 融合 |
| 画像存储 | 数据库表 | md + json 文件 |
| 刷新机制 | 无 | 每周定时刷新 + diff json |

## 三、数据层设计

### 3.1 数据库表结构

数据库只保留两张表，负责数据归一化和意图提取的持久化。画像和变化报告不进数据库，直接输出为文件。

```sql
-- 1. 归一化原始数据
CREATE TABLE IF NOT EXISTS raw_data (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source TEXT NOT NULL,
    source_id TEXT,
    content TEXT NOT NULL,
    actions TEXT,
    outcome TEXT,
    learned TEXT,
    timestamp DATETIME NOT NULL,
    raw_json TEXT,
    ingested_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(source, source_id)
);

-- 2. LLM提取的用户意图
CREATE TABLE IF NOT EXISTS llm_intents (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    raw_data_id INTEGER NOT NULL,
    intent_category TEXT,
    intent_summary TEXT,
    keywords TEXT,
    sentiment TEXT,
    priority TEXT,
    project_name TEXT,
    llm_model TEXT,           -- LLM 模型名 或 'rule_short'（短文本直接入库）
    extracted_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (raw_data_id) REFERENCES raw_data(id)
);
```

### 3.2 意图提取策略

| 内容长度 | 处理方式 | llm_model |
|----------|---------|-----------|
| < 100 字符 | 直接用原文作为 intent_summary，category 标为"短消息" | `rule_short` |
| >= 100 字符 | 批量调用 LLM 提取结构化意图 | `LongCat-2.0` |

短文本本身就是意图，不需要 LLM 压缩。实际数据中 96-99% 的记录是短文本，这大幅减少了 API 调用。

### 3.3 归一化数据结构

`raw_data` 表统一各 channel 的字段：

| 字段 | 说明 | trae 来源 | marvis 来源 |
|------|------|----------|------------|
| source | channel 名 | trae | marvis |
| source_id | 原始记录唯一标识 | message_id | id 或 created_at+hash |
| content | 消息内容/意图 | intent | content |
| actions | 执行动作列表 | actions | [] |
| outcome | 结果 | outcome | "" |
| learned | 学到的东西列表 | learned | [] |
| timestamp | 归一化时间 | message_summary_time | created_at |
| raw_json | 原始 JSON 备查 | 整行 JSON | 整行 dict |

## 四、画像维度设计

画像回答 5 个核心问题，每个问题对应一个可观测维度。

### 4.1 方向真实度

问题：你声称的方向 vs 实际在做的方向，gap 多大？

| 项 | 内容 |
|----|------|
| 数据源 | trae 聊天记录（LLM 提取意图后聚合） |
| 产出 | 方向漂移检测报告（按周/月） |
| 反哺 | 信息层 SOP 第零层 · 方向校准 |
| 判断逻辑 | LLM 对意图分类后，统计 Agent/Memory 相关意图占比 |

### 4.2 知识兴趣光谱

问题：你真正在消费什么内容？

| 项 | 内容 |
|----|------|
| 数据源 | bilibili 观看历史、trae 讨论主题 |
| 产出 | 兴趣分布 + 深度 vs 碎片比例 |
| 反哺 | 信息层 SOP 第一层 · 信源审计 |
| 判断逻辑 | 内容分类分布、时长分布、知识类 vs 娱乐类比例 |

#### 数据可行性（2026-07-11 POC · 实测）

`bili history --json` 原生字段仅含 `bvid / title / author / viewed_at`，**无时长、无分区**。但经补抓取验证可行：

| 补充来源 | 接口 | 拿到字段 |
|----------|------|---------|
| 时长 | `api.bilibili.com/x/web-interface/view?bvid=` | duration(秒) ✅ |
| 兴趣/分区分类 | 标题关键词本地规则（classify()） | tag 接口批量被 B站风控 412，弃用；view 仅补 duration+tid |

结论：时长经 view API 稳定补全；兴趣分类因 tag 接口（`x/tag/archive/tags`）批量被 B站风控返回 412，改回标题关键词本地规则（零网络依赖），每个 bvid 仅 1 次 view 请求。

### 4.3 作息精力模式

问题：你的高效时段是什么时候？

| 项 | 内容 |
|----|------|
| 数据源 | trae/marvis 活跃时间戳、weiTracker 拍照时间 |
| 产出 | 24 小时活跃度分布（文字版热力图） |
| 反哺 | 信息层 SOP 第二层 · L3 时间预算安排 |
| 判断逻辑 | 按小时统计活跃频次，识别峰值时段 |

### 4.4 决策行动模式

问题：你遇到问题时怎么处理？

| 项 | 内容 |
|----|------|
| 数据源 | trae 聊天记录（LLM 提取的意图 category + actions） |
| 产出 | 决策模式画像（先调研 vs 先动手、想法到行动的间隔） |
| 反哺 | 工作流优化 |
| 判断逻辑 | LLM 判断意图类别，统计调研/动手/讨论占比 |

### 4.5 情绪审美倾向

问题：你的情绪状态和审美偏好是什么？

| 项 | 内容 |
|----|------|
| 数据源 | 网易云听歌历史（ncm）、bilibili 内容类型 |
| 产出 | 审美偏好标签、重复播放画像 |
| 反哺 | 自我状态监测 |
| 判断逻辑 | 重复播放模式、时长分布（ncm）；内容类型（bili） |

#### 数据可行性（2026-07-11 POC · 实测）

对 ncm 三个命令的 JSON 输出做了字段审计：

| ncm 命令 | 可用字段 | 缺失字段 |
|----------|---------|---------|
| `ncm record` | playCount(重复次数)、score、song{id,name,ar,al,dt时长} | 播放时间戳、风格/标签 |
| `ncm song <id>` | id,name,ar,al,dt,privileges | 风格/标签/流派 |
| `ncm search song` | id,name,ar,al,dt,privilege | 风格/标签 |

结论：**ncm 所有命令的 JSON 均不返回音乐风格（genre/标签/流派）字段，也不返回播放时间戳**（ncm 无 album/artist 命令可间接取风格）。

| 画像维度 | 状态 | 说明 |
|----------|------|------|
| 音乐风格分布 | ❌ 降级 | ncm 无风格字段，CLI 也无 album/artist 子命令，暂无法获取；网易云私有风格接口需 cookie，不引入 |
| 播放时段 | ❌ 降级 | record 仅有 playCount/score，无"何时播放"时间戳 |
| 重复播放模式 | ✅ 保留 | 用 playCount 识别单曲循环 / 高复听 |
| 时长分布 | ✅ 保留 | 用 song.dt（歌曲时长，非收听行为，标注为间接代理） |

## 六、LLM 语义层设计

### 6.1 意图提取

对每个 `raw_data` 记录，调用 LLM 提取：

```json
{
  "category": "技术探索|项目实施|问题排查|学习了解|生活诉求|其他",
  "summary": "一句话概括用户意图",
  "keywords": ["关键词1", "关键词2"],
  "sentiment": "positive|neutral|frustrated|curious|excited",
  "priority": "high|medium|low",
  "project": "关联项目名称"
}
```

### 6.2 分 channel 画像生成

对 trae、marvis 等 channel，把该周期内的意图列表输入 LLM，生成分 channel 画像。

### 6.3 综合画像融合

把各 channel 画像输入 LLM，生成覆盖 5 个维度的综合画像。

### 6.4 LLM 配置

| 配置项 | 值 |
|--------|---|
| 服务商 | LongCat |
| 接口 | OpenAI 兼容接口 `https://api.longcat.chat/openai/v1/chat/completions` |
| 模型 | LongCat-2.0 |
| API Key | 环境变量 `LONGCAT_API_KEY` |
| 调用方式 | 标准库 `urllib.request` |
| 短文本跳过 | < 100 字符直接入库，不调 LLM |

### 6.5 降级策略

当 LLM 不可用时：
- 意图提取暂停
- 各 channel 分析回退到 `analysis/*.analyze()` 规则版
- 综合画像由 `aggregator._build_rule()` 做基础拼接

## 七、技术方案

### 7.1 核心决策

- 不引入 HPI 框架
- SQLite 作为本地数据仓库
- LLM 驱动语义分析
- 规则分析作为 fallback
- 保持现有目录结构

### 7.2 技术选型

| 层级 | 技术 |
|------|------|
| 语言 | Python 3.9+ |
| 数据库 | sqlite3 |
| LLM 调用 | urllib.request + OpenAI 兼容接口 |
| 数据结构 | @dataclass |
| 定时刷新 | Windows 计划任务 / scheduler.py |
| 产出 | Markdown |

### 7.3 流水线命令

```bash
# 1. 入库
python -m profile.cli.ingest

# 2. 意图提取（需要 LLM Key）
python -m profile.cli.extract_intents

# 3. 生成画像
python -m profile.cli.generate_profiles

# 4. 每周一键刷新（整合 1+2+3+diff）
python -m profile.cli.refresh_all
```

## 八、变化追踪与量化自我

### 8.1 变化标记机制

每次刷新后，读取上次的 `*.json` 文件与本次生成的画像做 diff：

| 变化类型 | 触发条件 |
|----------|----------|
| new | 新字段出现 |
| increased | 数值/占比上升 |
| decreased | 数值/占比下降 |
| disappeared | 原有字段消失 |
| changed | 其他变化 |

### 8.2 每周刷新产出

除综合画像外，额外产出 `个人画像-变化报告-YYYY-MM-DD.md`：

```markdown
# 个人画像变化报告 · 2026-07-11

## 本周变化
- [新增] 新关注方向："量化自我"
- [上升] Agent 相关讨论占比从 3.3% 上升到 12%
- [下降] 日均活跃次数从 21.7 下降到 15

## 详情
| 类型 | 字段 | 旧值 | 新值 |
|------|------|------|------|
...
```

diff 数据来源是 `画像产出/` 目录下最近一次的 `*.json` 文件，不需要数据库。

## 十、与现有体系的关联

### 10.1 信息层 SOP 的闭环

```
信息层 SOP                          个人画像
---------                          --------
第零层 · 方向校准  <--- 反哺 ---  方向真实度（画像维度1）
第一层 · 信源审计  <--- 反哺 ---  知识兴趣光谱（画像维度2）
第二层 · L3时间预算 <--- 反哺 ---  作息精力模式（画像维度3）
```

### 10.2 方向锚点

当前方向档案：
- 主方向：Agent
- 次方向：Memory

画像的方向真实度分析会直接检验实际讨论主题与这两个方向的重合度。

## 十一、风险与应对

| 风险 | 概率 | 应对 |
|------|------|------|
| LLM API 不可用 / 超时 | 中 | LLM_FALLBACK_TO_RULES = True，回退到规则分析 |
| LLM 返回 JSON 格式异常 | 中 | client.py 内置多种 JSON 提取策略 |
| bili-cli / 网易云 API 不可用 | 中 | Phase 2 开始前先验证数据链路，不通则跳过 |
| marvis SQLite 读取时被锁 | 中 | ETL 先复制 data.db 到临时目录再读 |
| 数据量不够分析不出趋势 | 中 | 标注"样本不足，待积累" |
| 画像文档变成"写了不看" | 高 | 与操作台月度校准绑定 |
