# repo-hygiene — mono 仓库体检

目标只有一个：让"工作区干净"和"文档与代码不失真"成为**被验证过的事实**，而不是假设。
本仓库根 AGENTS.md 的 R4（小步提交）、R5（三处同步不失真）、R7（质量门禁）是判断标准，先读它再动手。

## 流程总览（按序执行，不可跳步）

1. **提交完整性盘点** → 2. **质量门禁** → 3. **文档-代码一致性核查** → 4. **分组提交** → 5. **体检报告**

### 1. 提交完整性盘点

```
git status --short          # 未暂存/已暂存/未跟踪
git log --oneline origin/main..HEAD   # 本地领先多少（是否该 push 问用户）
git diff --cached --stat    # 已暂存的部分要单独看——说明有人提交到一半
git diff --stat             # 未暂存
```

- 已暂存 + 未暂存并存 = 提交被打断过，两组改动要**分别审阅**，不能一把 `git add -A`。
- 未跟踪文件逐个判断去向：业务测试进 `apps/<name>/tests/`；一次性预览/草稿页问用户或注明用途后提交；运行时产物（db/log/png）绝不提交（R11），应确认已在 .gitignore。
- 分组标准（R4）：一个提交只做一件事；`docs 变更单独成提交`，不与代码混提；跨包联动 scope 写明所涉包。
- **没有用户明确要求不 push。**

### 2. 质量门禁（提交前必须全绿，R7）

```
uv run ruff check apps packages tests
uv run --all-packages pytest -q          # 全量约 10 分钟；只测单个 app 可 cd 进去跑
node apps/mermaid-viewer/tests/check_prompt_logic.js   # 非 pytest 体系的应用脚本测试也要跑
```

- 门禁不绿禁止提交；测试失败要如实报告输出，禁止"再跑一次碰运气"。
- 注意 uv workspace 陷阱：涉及成员包的命令必须带 `--all-packages` 或 `--package <name>`。

### 3. 文档-代码一致性核查（R5 三处同步）

**必读模块**（每次体检都要打开，不许凭记忆）：

| 读什么 | 为什么 |
|---|---|
| 根 `AGENTS.md`（R4/R5/R7 三条） | 判断标准在此 |
| 各 app 的 `ROADMAP.md` 末尾 2-3 条执行记录 | 最新改动的主张都在这 |
| 对应 `docs/<app>-tech.md` 涉及改动的章节 | 接口/表结构/数据流的契约 |
| 对应 `docs/architecture-flow.mmd` | 图中参数是最易漂移的部位 |
| `git diff`（未提交时）/ `git show --stat`（核查已提交时） | 实际改了什么以 diff 为准，不以文档自述为准 |

**必须亲自验证、不能采信文档自述的点**（按漂移风险排序）：

1. **架构图里的具体数字/参数**：轮询间隔、阈值、k 值、工具数量、重试次数。必须 grep 源码常量逐一对照（如 `_POLL_INTERVAL_SECONDS`、`threshold=0.45`、清点 `TOOL_NAMES` 个数）。图里的数字最容易出现"上次是对的、这次改代码没回头改图"。
2. **符号名/字段名三处一字不差**：tech 文档说的函数名、GAState 字段、路由路径，要能在源码里精确定位（给 文件:行号）。拼错或改名的符号是 R5 判定的"代码缺陷级"失真。
3. **ROADMAP"实测验证"小节的主张**：声称"N 项测试全绿""断言 13 项全过"，能廉价复跑的（脚本测试、单 app pytest）就复跑确认；不能复跑的（真实 API 调用、当日数据）标注"无法复核"而不是默认采信。
4. **tech 文档里的行号引用**（如 "tools:80-106"）：极易漂移，属于低危瑕疵——核对后若漂移，记入报告的低优先级项，可顺手修但单独 docs 提交。
5. **架构图节点可回溯性**：每个节点引用的函数/类名在源码中存在；有 `UNVERIFIED`/`MISSING` 标记的节点按 codemap skill 流程处理，不得手改了事。

**核查范围的选择**：
- 有未提交代码改动 → 逐个改动点核对三处同步（提交前检查清单的强制项）。
- 工作区干净、做例行体检 → 用 `git log --oneline -5` 取最近提交抽查；改动横跨多模块或多文件时，按 app 拆给 Explore 子代理并行核查（提示词要求"逐项给 一致/不一致 结论 + 文件:行号 证据"，这是本 skill 验证过的有效模式）。
- 深度走查架构图时调用 `codemap` skill，不要手查。

### 4. 分组提交（工作区不干净时）

顺序建议：代码修复 → 配置/脚本 → 应用内新增测试 → `docs(scope): ...` 收尾。
提交信息格式 `type(scope): 描述` + 空行 + 要点正文（做了什么/为什么/验证方式）。

### 5. 体检报告（最终输出固定结构）

```
## 提交状态
- 工作区：干净 / N 个未提交（列出并说明去向）
- 分支：领先 origin/main N 个提交（是否 push 待用户定）

## 质量门禁
- ruff：PASS/FAIL（输出）
- pytest：N passed, M skipped（耗时）
- 其他脚本测试：各自结果

## 文档-代码一致性
- 逐项：一致 / 不一致（证据：文档写 X，代码实际 Y，文件:行号）
- 低危瑕疵（行号漂移等）单列

## 已采取的动作 / 待用户决定
```

报告必须忠实：失败的测试贴输出，没验证的说没验证，禁止"应该没问题"。
